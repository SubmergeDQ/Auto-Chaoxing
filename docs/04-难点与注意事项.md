# 04 · 难点与注意事项

这份文档回答两个问题：**哪里会卡住你**（难点），**哪些坑踩了会白干**（注意事项）。

---

## 一、技术难点（按"会卡多久"排序）

### 1. 作业提交接口是黑盒（最不确定）

刷视频是"纯计算 + GET"，作业是"提交一坨表单，错了平台静默丢弃"。

- 页面里的 `submitData()` 会拼一批隐藏字段（`workAnswerId`、`temAnswer`、`totalQuestionNum`、
  `fullScore`、`pyFlag`…），字段随作业类型（作业/测验/考试）变化。
- 纯 HTTP 复刻需要一次完整抓包；在拿到之前，**用隐藏 WebView 执行页面自己的函数**是唯一稳的路线。
- 判断成功的唯一标准：回读 `work/task-list` 看到 `completed`。

> 结论：作业模块的工期风险 80% 集中在这里。先做「拉题 + 解析 + 展示」，再决定提交走 WebView 还是 HTTP。

### 2. 视频反作弊字段

上报不止 `enc` 一个签名：

| 字段 | 作用 | 处理 |
|---|---|---|
| `enc` | 进度签名，可本地算 | ✅ 已实现 |
| `dtoken` | 每次 status 生成，短时效 | 每次现取，不缓存 |
| `attDuration` / `attDurationEnc` | 任务点累计时长校验 | 从卡片原样回传 |
| `videoFaceCaptureEnc` | 人脸抽检凭证 | 原样回传；平台要求采集时停 |

任何一项没带对，平台会返回 200 但进度不涨——**最难查的一类问题**，所以日志必须记录请求全文（脱敏后）。

### 3. 人脸抽检（无法绕过，只能降级）

部分课程会周期性要求"本人照片比对"。纯协议路线只能：

1. 用户提前上传一张本人照片（存本地，加密）；
2. 抽检时走 `check-face-result` + `faceEnc` 提交；
3. 比对失败 → `needs_attention`，停止该任务点，不重试。

不要为了让进度变绿去反复提交随机照片：那是最容易触发风控的行为。

### 4. 章节顺序依赖

- 章节测试没提交，下一章 `mArg` 不返回 → 看着像"解析失败"，其实是业务前置。
- 任务点未完成，某些章节不放行。
- 处理：把「mArg 缺失」单独归类为 `ChapterLocked`，提示"上一章未完成/测验未交"，而不是报解析错误。

### 5. 题目解析的脏活

- 富文本题干：HTML 实体（`&nbsp;`、`&lt;`）、图片题（题干是 `<img>`）、公式（MathML）。
- 填空题：新版 `input.answerInput`，旧版是 `ueditor` iframe 里的 `<p>`；iframe 需要等加载。
- 判断题伪装成选择题（两个选项是"正确/错误"）→ 需要题型纠偏。
- 多选答案顺序：平台按 ASCII 排序拼接，顺序错了算错。

### 6. 登录态与验证码

- 密码登录有概率直接要验证码；有二次验证的学校必须走 WebView。
- WebView 登录后 cookie 里有 `HttpOnly` 项，**JS 读不到**，必须用平台的 CookieManager API 取。
- 多账号：每个账号独立 CookieJar + 独立数据目录，不能共用。

### 7. 平台风控（已知的三个"清零"触发器）

1. 倍速 > 2（部分视频直接清空进度）；
2. 同账号多端同时刷；
3. 夜间长时间挂机（脚本社区里反复出现的提示）。

应对：步长固定 60s、单账号串行、夜间暂停、每章结束回读平台状态确认。

### 8. 幂等与"看起来成功"

- 签到：同一 `activeId` 成功过就不再发；提交结果不明时**停**，不要重发。
- 作业：提交后必须回读；本地"已提交"标记不可信。
- 视频：以 `isPassed` 为准，不以"请求 200"为准。

## 二、Flutter 双端的特有难点

| 难点 | 表现 | 处理 |
|---|---|---|
| Android 后台被杀 | 熄屏 10 分钟后任务停 | 前台服务 + 常驻通知 + 引导关闭电池优化 |
| WebView 注入差异 | `flutter_inappwebview` 有 `userScript`，Windows 的 WebView2 包装库基本只有 `ExecuteScriptAsync` | 注入逻辑放 Android；Windows 走纯 HTTP 降级 |
| Cookie 双份 | dio 的 CookieJar 与 WebView 的 cookie 是两套 | 以 CookieJar 为准，登录完成后从 CookieManager 一次性导入 |
| 通知 | `flutter_local_notifications` 在 Windows 支持有限 | Windows 用应用内提示 + 托盘气泡 |
| 托盘/最小化 | Windows 需要托盘常驻 | `tray_manager`，默认关闭 |
| 高 DPI / 字体 | 两端渲染差异 | 统一用 `MediaQuery.textScaler` 与自适应断点 |
| 打包体积 | Android 分包 | `--split-per-abi` |

> 原则：**业务代码共享，平台能力抽象**。`lib/platform/platform_services.dart` 是唯一允许出现
> `Platform.isAndroid` 的地方。

## 三、注意事项（踩了会白干的清单）

### 安全与隐私

1. **日志里不许出现**：密码、cookie 原文、手机号、姓名、学号。导出诊断包前二次脱敏。
2. cookie 存 `flutter_secure_storage`（Android Keystore / Windows DPAPI），不要写进 sqlite 明文。
3. 不要把用户的题库 token 打进日志或提交进仓库。

### 行为约束

4. 单账号串行，不并发；同一任务点不重复提交。
5. 遇到 `needs_attention`（人脸/验证码/风控提示）**必须停**，把决定权交回用户。
6. 不实现自动交卷；考试只做提醒与题目搬运。
7. 不对同一 `activeId` 连续签到轰炸（平台会直接判异常）。

### 工程约束

8. `core/` 不允许依赖 Flutter，保证能被纯 Dart 单测覆盖；协议逻辑全部在这一层。
9. 每次协议字段变更，同步更新：模型 → 解析 → 单测向量 → `docs/03` 表格。缺一项就算没改完。
10. `checkpoint` 要带版本号；升级后旧断点要么能读，要么明确丢弃并提示，不要静默跑错章节。
11. 长任务要限制日志数量（建议 5000 条环形缓冲），否则 Windows 端内存会一路涨。
12. 时区与服务器时间：签到判断用服务器返回的 `startTime/endTime`，不要用本地时间硬算。

### 维护约束

13. 题库、协议、页面结构都可能变。所有外部依赖都要有"失败就降级"的分支，而不是抛异常崩掉。
14. 每个版本至少在真机上完整跑一遍：登录 → 一章视频 → 一次签到 → 一份作业。
15. 记录"上次成功的协议指纹"（如 `mArg` 字段集合），启动时比对，变化时提示可能改版。

---

## 四、一句话总结

刷视频是**数学题**（已经解完），作业是**工程题**（接口要抓、页面要解析），
考试是**对抗题**（不建议做）。真正的长期成本不是写代码，是**跟着平台改版维护解析层**。
