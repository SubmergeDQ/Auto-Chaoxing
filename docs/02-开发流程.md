# 02 · 开发流程

## 1. 环境准备

### 通用

```bash
flutter --version     # 需要 3.24+（Dart 3.5+）
flutter doctor -v     # 三项必须全绿：Dart、对应平台工具链、设备
```

### Android

- JDK 17（Android Gradle Plugin 8.x 要求）
- Android SDK Platform 35 + Build-Tools 35
- 真机调试优先：模拟器上后台保活与省电策略与真机差异很大，签到类功能必须真机验证

```bash
flutter run -d <device-id>
flutter build apk --release --split-per-abi
```

### Windows

- Visual Studio 2022，勾选「使用 C++ 的桌面开发」（含 MSVC v143 + Windows 10/11 SDK）
- 开启开发者模式（`start ms-settings:developers`），否则插件符号链接失败

```bash
flutter run -d windows
flutter build windows --release
```

### 依赖锁定

`pubspec.yaml` 中第三方插件先用 `any` 起步，**首次 `flutter pub get` 成功后立刻回填精确版本并提交
`pubspec.lock`**。原因：这类插件迭代快，宽范围会让一台机器能编译、另一台不能。

## 2. 里程碑

| 阶段 | 目标 | 产出 | 验收 |
|---|---|---|---|
| M0 协议验证 | 确认学习通链路仍有效 | `core/chaoxing_core.py` 跑通登录→课程→视频 | 任务点在网页后台变绿 |
| M1 骨架 | 双端能起来、能登录、能列课程 | Flutter 工程 + 登录页 + 课程页 | 两端 UI 一致，cookie 落盘 |
| M2 刷课 | 视频任务点全自动 | TaskRunner + 日志页 | 一章视频全部通过，可中断续跑 |
| M3 签到 | 轮询 + 通知 + 定位参数 | 签到页 + 前台服务 | 活动发起 60s 内签上 |
| M4 作业 | 题目解析 + 题库 + 提交 | 作业页 + AnswerProvider | 提交后平台 `completed` |
| M5 打磨 | 稳定性、导出诊断、打包发布 | APK / Windows 安装包 | 连续 3 天挂机不崩 |

时间预估（单人）：M0 已基本完成，M1 ≈ 1 周，M2 ≈ 1 周，M3 ≈ 1 周，M4 ≈ 2–3 周，M5 ≈ 1 周。
**双端比单端多约 20–30%**，成本集中在 Windows 的 WebView 与打包，而不是业务代码。

## 3. 分支与提交

```
main            ← 始终可构建
feat/<模块>     ← 功能分支，例：feat/video-runner
fix/<问题>      ← 修复分支
docs/<主题>     ← 纯文档
```

提交信息用 Conventional Commits，中文正文：

```
feat(core): 实现视频进度签名与串行上报
fix(android): 修复前台服务被系统回收后 checkpoint 丢失
docs: 补充作业提交接口的实测结论
```

一个提交只做一件事；协议参数变更**必须**在提交正文里写清「改了什么字段、依据什么证据」。

## 4. 代码规范

- `flutter analyze` 必须零 issue；`analysis_options.yaml` 已开启 `flutter_lints` + 若干强规则。
- 单文件 ≤ 400 行；`core/` 下禁止 `import 'package:flutter/...'`（保证可被纯 Dart 单测覆盖）。
- 所有对外方法返回 `Result<T>`，不用异常跨层。
- 新增协议字段时，同时补：模型字段、解析、单测向量、`docs/03` 表格一行。

## 5. 测试策略

| 层级 | 工具 | 覆盖什么 | 门槛 |
|---|---|---|---|
| 单元 | `dart test` / `flutter test` | 加密、签名、解析、节流器、状态机 | 核心算法 100% 分支 |
| 契约 | 录制样本 | 用真实 HTML 片段断言 `mArg` 解析 | 每类页面至少 1 份样本 |
| 集成 | `integration_test` | 登录 → 列课 → 刷一章（用测试账号） | 手动触发，不进 CI |
| 冒烟 | CI | `flutter analyze` + `flutter test` + 双端编译 | 每个 PR |

签名与加密必须有**固定向量**（见 `test/crypto_test.dart`），防止某次重构把盐或字段顺序改错。

## 6. CI

`.github/workflows/ci.yml` 三段：

1. `analyze-test`（ubuntu）：`flutter analyze` + `flutter test`
2. `build-android`（ubuntu）：`flutter build apk --debug`
3. `build-windows`（windows-latest）：`flutter build windows --release`

> 首次运行前请在仓库设置里确认 Actions 可用；CI 文件为初版，尚未在本仓库实际跑过。

## 7. 发布

### Android

```bash
keytool -genkey -v -keystore release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias auto
flutter build apk --release --split-per-abi --dart-define=... 
```

- 签名文件与口令**不入库**，走 CI Secrets。
- 首次安装提醒用户关闭电池优化（这是后台任务被杀的首要原因）。

### Windows

```bash
flutter build windows --release
# 产物在 build/windows/x64/runner/Release/
```

- 分发 zip 或 MSIX；未签名包首次运行会被 SmartScreen 拦截，属预期行为。
- 如需开机自启与托盘，在设置页给出开关，不默认开启。

## 8. 协议变更应对流程

学习通改版时按这个顺序处理，别直接改代码：

1. 用 `core/chaoxing_core.py` 复现失败，**保留原始请求与响应**；
2. 对比 `docs/03-协议与接口.md` 里的字段表，定位是「字段变了」还是「结构变了」；
3. 只改解析层（`Parser`）或签名层（`Crypto`），保持 TaskRunner 不动；
4. 更新文档表格 + 加一条回归向量；
5. 版本号 +1，CHANGELOG 写清「适配 xx 改版」。

## 9. 验收清单（每次发布前）

- [ ] 双端 `flutter analyze` 零 issue
- [ ] `flutter test` 全绿，`pubspec.lock` 无未提交变更
- [ ] 真实账号跑通：登录 → 一章视频 → 一次签到
- [ ] 断网中途、强制杀进程后能续跑
- [ ] 日志导出不含 cookie / 密码 / 手机号
- [ ] Android 前台服务通知文案正确，可一键停止
